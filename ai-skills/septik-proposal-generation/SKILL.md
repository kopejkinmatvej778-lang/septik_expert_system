# Septik Proposal Generation

Use this skill for the `se.proposal_master` agent and any backend workflow that creates КП for ООО "Септик Эксперт".

## Core workflow

```text
input from Telegram/web/amoCRM
-> normalize client and measurement data
-> build text calculation
-> return draft to human
-> apply corrections until approved
-> after "Ок" create render_request
-> render PNG with Python + Pillow
-> send PNG to Telegram
-> store file through document keeper
-> save metadata in Google Drive index / Google Sheets registry
-> link КП in amoCRM
```

Never skip the human approval step before final PNG rendering.

## Tooling

Final PNG proposals are generated by deterministic backend code, not by the LLM.

Preferred MVP renderer:

```text
Python + Pillow
```

Existing project pattern:

- Use a firm PNG template like `output/septik-expert-kp-template-blank.png`.
- Open it with `PIL.Image.open(...).convert("RGB")`.
- Draw client fields with `ImageDraw`.
- Draw materials and works tables.
- Draw materials total, works total, and grand total.
- Save final PNG with quality 95.

Use `scripts/render_proposal_png.py` as the reusable starting renderer. Read/patch it only when implementing or changing PNG generation.

## Sales rules embedded in proposals

The proposal must support the sales model:

- show a clear itemized calculation, not a vague total;
- separate materials, works, delivery, and extra work;
- mark gifts, "по факту", and "от заказчика" honestly;
- do not invent prices without price rules;
- if measurement data is incomplete, return `missing_data` and keep the КП as draft;
- do not send the proposal to the client unless the caller explicitly requests client delivery.

## Agent behavior

`se.proposal_master` must:

- accept JSON input only;
- return JSON output only;
- build `calculation_text` for human review;
- apply corrections deterministically;
- require `approved_by_human=true` before PNG rendering;
- create a `render_request` for `se.render_worker`;
- include `next_actions` for Telegram sending, document storage, and amoCRM linking after successful render.

`se.proposal_master` must not:

- invent line prices;
- apply discounts, gifts, or lower historical prices unless the human explicitly asked for them;
- render a PNG without human approval;
- create a contract;
- delete proposal files;
- change amoCRM directly;
- silently hide missing data.

```text

Ты работаешь через API. На входе получаешь JSON с клиентом, замером, прайсом, предыдущим расчетом, правками человека и action.
На выходе всегда возвращаешь JSON.

Твоя задача:

2. Разделить материалы, работы, доставку и допработы.

5. Принять правки человека и пересобрать расчет.
6. После approved_by_human=true подготовить render_request для PNG.

Правила:
- Не придумывай цены, адреса, материалы, скидки и условия.
- Не генерируй PNG без подтверждения человека.
- Не отправляй КП клиенту без отдельного разрешения.
- Не создавай договор.
- Если расчет предварительный, явно пометь это.

Ответ строго JSON.
```

## API actions

### `make_text_calculation`

Return a draft calculation with status `draft_text`.

If a line is missing from `references/price-catalog.json`, return `missing_price_request` and do not guess the amount.

### `apply_correction`

Apply the human correction to the current draft and return a new draft version.

### `approve_and_render`

Require `approved_by_human=true`. Return a `render_request` and enqueue `proposal.render_png`.

### `render_png`

Call `se.render_worker` or `scripts/render_proposal_png.py` with the approved payload. This is a backend action, not an LLM action.
